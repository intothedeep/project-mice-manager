- **Task model v2 — CASES + TASK_EVENTS (DECIDED 2026-09-13, user):**
  - **Lifecycle EXTENDED:** open|done|verified|cancelled → **todo → doing →
    done → verified**, with **cancelled** as a side-exit. `doing` = a staff
    member has claimed/started the work — the WIP visibility the old
    lifecycle lacked.
  - **Two-table CASE model — SUPERSEDES the single `tasks` table versioned
    by `origin_task_id`.** `cases` = the STABLE work-item identity:
    case_type, signal, subject FKs (incl. NEW `subject_mate_id`, below),
    gen_key, `current_status` (a sanctioned DERIVED CACHE — truth =
    task_events, same class as the R1 `mice.cage_id` cache), due_date,
    created_by. Each case has-many `task_events` = APPEND-ONLY transitions
    (status, actor, note, ts). Supersession scope is TASKS ONLY:
    `notes`/`mates`/`mice` keep the origin-id versioning + prev_id CAS
    unchanged. (This records the model decision; the migration path for the
    existing `tasks` table is 0021's concern — no drop is decided here.)
  - **gen_key idempotency for auto-generated cases:** a plain PARTIAL UNIQUE
    (`WHERE deleted_at IS NULL`) on the IMMUTABLE `cases` table. This
    RESOLVES the R10 cost line "UNIQUE constraints cannot be placed on
    mutable fields" — case identity no longer versions, so the constraint
    has a stable home. Key = ruleKey + triggering-fact ORIGIN id (e.g.
    `plug_check:mate=<id>`), NEVER keyed on run date. Re-arm rule: a
    CANCELLED case is NOT regenerated — its gen_key survives cancel.
  - **NEW `subject_mate_id` FK on `cases` (known schema gap, now closed):**
    a plug-check's subject is a MATE CYCLE, which predates any litter row —
    no existing subject FK could hold it.
  - **Overdue is DERIVED AT READ, never stored:** `current_status IN
    (todo, doing) AND due_date < today`; the grid renders a coral/red THICK
    BORDER. Same compute-at-read discipline as `lifeStage` /
    `countSlotAdults`.
  - **System/service user:** auto-generation needs a system user to stand as
    `cases.created_by` (non-human `users` row, same stub-identity table).
  - **SOP automation scope (YAGNI):** hard-code the two SOPs — plug-check
    and genotyping — behind a pure **TaskGenerator** seam + an event-driven
    runner in `colony_server`. The general user-authored macro/rule engine
    is DEFERRED to P1+ — when it lands it becomes just one more
    TaskGenerator, zero rework. NOTE: the earlier `task_offset_rules` config
    table already covers "tune thresholds without a deploy". NOTE: genotyping
    detection must read the `genes`/`mice_genes` schema — `mouse_events` was
    DROPPED in migration 0016.
  - **REFINED 2026-09-13 (user) — task-centric naming + subject set** (this
    supersedes the `task_events` naming above and its framing as a log
    distinct from "tasks"; the rest of the v2 model stands):
    - **`task_events` is RENAMED to child `tasks`** — IMMUTABLE, append-only
      STATUS RECORDS under a case: each row = the status the case moved to
      (todo|doing|done|verified|cancelled) + case_id + actor + note +
      created_at. A task's status is assigned at creation and NEVER changes
      (redundant with the case's status by design — a useful audit trail).
    - **`cases.current_status` = MUTABLE rollup (kept):** advancing a case =
      INSERT one new child `tasks` row + UPDATE `cases.current_status`, in
      ONE service transaction.
    - **Creating work = a `cases` row + its FIRST `todo` task** in one
      transaction; SOP generators emit exactly the same shape.
    - ~~**Batch over N mice = N separate cases** (one per mouse), each with
      its own first task — never one case fanning out to N subjects.~~

    - **BATCH = ONE case over N mice (DECIDED 2026-09-14, user — REVERSES the
      struck bullet above; USER-created batches only):** a batch task over N
      selected mice is ONE `cases` row (single case_id) covering all N. All
      members do the SAME task and ADVANCE TOGETHER as one unit — the case
      has ONE `current_status`; there is intentionally NO per-mouse
      independent progress.
      - **Schema (additive, migration `0024_case_mice.sql`):** a batch case
        uses NEW `subject_kind='mice'` (all six single-subject FKs NULL);
        membership lives in a new `case_mice(case_id, mouse_id)` join —
        partial-unique `(case_id, mouse_id) WHERE deleted_at IS NULL` +
        lookup indexes on case_id and mouse_id. SINGLE-subject cases are
        UNCHANGED (`subject_kind='mouse'` + `subject_mouse_id`); SOP
        generators (genotype = 1 mouse, plug_check = 1 mate) are UNTOUCHED —
        their per-fact N-cases fan-out stands. `cases_subject_kind_check` +
        `cases_subject_matches_kind` widened with a `'mice'` branch (all FKs
        NULL). Non-breaking.
      - **Grid badges are DERIVED from the case store** (the hardcoded
        `MouseCell.activeTasks` is REMOVED): a mouse shows a badge iff it is
        a member of an OPEN case (status ∈ {todo, doing}) — resolved via
        `subject_mouse_id` (single) or `case_mice` membership (batch),
        grouped by signal; `TaskSignal`→`SignalColor` mapping
        (`note`→`'flag'`). Perf: memoized `Map<metaId, tags[]>`,
        O(mice + members).
      - **Mock is schema-faithful + id-keyed** (subject by `mouse_meta.id` /
        metaId, NOT label strings) — fixes a real bug where a duplicated
        rendered id (`F5AYL` at metaId 102 AND 402) made the drawer show the
        wrong mouse's cases.
      - **UI:** a batch case renders as ONE card showing its N-member list;
        `/tasks` needs no extra grouping (it is genuinely one case_id).
    - **subject_kind = mouse | cage | slot | litter | mate | line** —
      'room' is REMOVED from the earlier subject set; 'slot' and 'line' are
      ADDED, with NEW `subject_slot_id` / `subject_line_id` FKs alongside
      the existing subject FKs.
    - **UI stays TASK-centric:** users create and work with "tasks"; the
      `/tasks` route and the "Tasks" nav are KEPT. "case" is an INTERNAL
      grouping (a work item + its status history) users mostly never see.
