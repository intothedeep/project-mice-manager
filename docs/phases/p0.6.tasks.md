- [ ] Task assignment + group eligibility (R17/R18, 2026-09-05).
      `tasks.assigned_to` is ONE FK to `users`; a group is a users row with
      `type='group'`. Picker = `SELECT id, display_name, type FROM users WHERE
      deleted_at IS NULL`. "My tasks" = assigned directly to me OR to a group I
      belong to via `group_members`.
      **Group eligibility is a SERVICE rule, not a constraint:** when
      `assigned_to` names a group, reject a transition whose actor is not in
      `group_members` for that group, with an explanatory error — the DB does
      not enforce this.
      **Authorization reads the ACTING PERSON'S role**, never the group's;
      `users.role` is NULL for groups by CHECK, so there is nothing to read.
      AC: a member of the assigned group can move the task open→done; a
      non-member is refused with a message naming the group; a task assigned
      directly to a person is unaffected; canTransition is called with the
      actor's role in both cases.
- [ ] **`appendVersion` repository helper — copy the head row, then override.**
      DECIDED 2026-09-05 (user): this is BUSINESS LOGIC in the backend, not a
      database constraint.
      Applies to ALL FOUR versioned-append tables, not just `mice`:
      | table | logical key | fields silently lost by a partial insert |
      |---|---|---|
      | `mice` | `mouse_meta_id` | cage, slot, sex, is_alive, attention, transit_status |
      | `mates` | `origin_mate_id` | mother, father, expected_delivery_on |
      | `tasks` | `origin_task_id` | subject_*, litter_id, due_date, **assigned_to**, direction |
      | `notes` | `origin_note_id` | subject_mouse_id, litter_id, meta |
      An append INSERT that omits a column gets its DEFAULT (usually NULL), and
      since the newest row IS the current state, the omitted value is destroyed
      silently — no error, no log. Measured (`flow-probes.sql` PROBEs 1, 6-8):
      marking a task `done` without carrying the row forward erased its
      assignee and subject cage; advancing a pairing erased both parents.
      NO SCHEMA CONSTRAINT CAN CATCH THIS: a NULL `cage_id` is also the
      legitimate "unplaced" state (P5) and a NULL `assigned_to` the legitimate
      "unassigned" state, so a constraint cannot tell an omission from an
      intention.
      Shape: `appendVersion(table, logicalId, changes, actor)` reads the current
      head row, copies EVERY column forward, applies `changes`, and inserts.
      Nothing may write these tables directly.
      AC: all four tables go through the helper; no `INSERT INTO mice|mates|
      tasks|notes` outside it; `flow-probes.sql` keeps the wrong form and the
      right form side by side for each table as a regression check.
      NOTE 2026-09-13: the `tasks` row of the table above is SUPERSEDED by the
      cases + task_events model (plan §4 Task model v2) — a task transition
      appends a `task_events` row (identity on `cases` never versions), so
      appendVersion no longer applies to tasks; mice/mates/notes stand.
      (task_events since RENAMED to child `tasks` — immutable status records
      under a case, plan §4 REFINED 2026-09-13; the supersession is unchanged.)

- [ ] **`MateRef.matedOn` must survive the server swap (added 2026-09-17).**
      The grid's mate cell shows the LATEST partner by sorting `matedOn`
      DESCENDING (`ColonyGridView.client.tsx`, mate cell). The field exists in
      `@repo/types` and in the mock fixtures; the colony-grid query must select
      `matings.mated_on` into it.
      WHY THIS IS A TRAP: if the query omits it, every `matedOn` is `null`, the
      sort degenerates to input order, and the cell silently shows whichever
      partner the join happened to return first — **wrong data, no error, no
      crash**. The mock fixture is deliberately built so the latest mate is the
      FIRST array element, so array-order fallbacks are visibly wrong.
      AC: a mouse with ≥2 matings renders the partner with the greatest
      `mated_on`; deliberate breakage — drop `mated_on` from the SELECT and
      confirm the rendered partner changes (then restore).
