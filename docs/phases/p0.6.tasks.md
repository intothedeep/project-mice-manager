- [ ] **`appendVersion` repository helper — copy the head row, then override.**
      DECIDED 2026-09-05 (user): this is BUSINESS LOGIC in the backend, not a
      database constraint.
      Applies to ALL FOUR versioned-append tables, not just `mice`:
      | table | logical key | fields silently lost by a partial insert |
      |---|---|---|
      | `mice` | `mouse_meta_id` | cage, slot, sex, is_alive, attention, transit_status |
      | `mates` | `origin_mate_id` | mother, father, expected_delivery_on |
      | `tasks` | `origin_task_id` | subject_*, litter_id, due_date, **assigned_to**, direction |
      | `notes` | `origin_note_id` | subject_mouse_id, litter_id, meta |
      An append INSERT that omits a column gets its DEFAULT (usually NULL), and
      since the newest row IS the current state, the omitted value is destroyed
      silently — no error, no log. Measured (`flow-probes.sql` PROBEs 1, 6-8):
      marking a task `done` without carrying the row forward erased its
      assignee and subject cage; advancing a pairing erased both parents.
      NO SCHEMA CONSTRAINT CAN CATCH THIS: a NULL `cage_id` is also the
      legitimate "unplaced" state (P5) and a NULL `assigned_to` the legitimate
      "unassigned" state, so a constraint cannot tell an omission from an
      intention.
      Shape: `appendVersion(table, logicalId, changes, actor)` reads the current
      head row, copies EVERY column forward, applies `changes`, and inserts.
      Nothing may write these tables directly.
      AC: all four tables go through the helper; no `INSERT INTO mice|mates|
      tasks|notes` outside it; `flow-probes.sql` keeps the wrong form and the
      right form side by side for each table as a regression check.
      NOTE 2026-09-13: the `tasks` row of the table above is SUPERSEDED by the
      cases + task_events model (plan §4 Task model v2) — a task transition
      appends a `task_events` row (identity on `cases` never versions), so
      appendVersion no longer applies to tasks; mice/mates/notes stand.
      (task_events since RENAMED to child `tasks` — immutable status records
      under a case, plan §4 REFINED 2026-09-13; the supersession is unchanged.)

- [ ] Litter-code allocation at INSERT (MOVED 2026-09-23 from
      `docs/phases/p0.7.tasks.md`, where it was "Litter-code generator"; still
      P0-b). **BLOCKED-BY a database:** the counter IS a Postgres sequence, so
      the wiring has nothing to call until `0002` has been applied.
      Also BLOCKED-BY the P0.3 codec fold — the codec is a client `lib/` today
      and a server may not import it.
      **MOST OF THIS TASK ALREADY EXISTS — verified 2026-09-23.**
      `packages/db/migrations/0002_core_tables.sql:243` declares
      `CREATE SEQUENCE litter_code_seq START 1612` and `:538` gives
      `litters.seq` the DEFAULT `nextval('litter_code_seq')`. 1611 = `BIY`, the
      workbook's last code, so the first issued value is 1612 = `BIZ`, the
      professor's recorded next code. The bijective base-26 codec exists too,
      mock-era, at `apps/colony_client_web/lib/litterCode.ts` (P0.3 folds it
      into `packages/domain` — do not rewrite it blind).
      WHAT IS LEFT is the wiring: when a `litters` row is created, read its
      `seq` and write `litter_code = encodeLitterCode(seq)`. The generator never
      emits a `+` offset (offsets live in the pup number only, plan §1) and
      never emits `WT`, a standing wild-type label outside the ordinal space
      (`lib/litterCode.ts` header).
      AC DEFECT CORRECTED IN THE MOVE: the criterion that came with this task —
      "no litter_seq value is written to any table" — is contradicted by
      `0002:538` (and by the task's own body, "persists litter_code + seq on the
      litters row"). Restated below as "exactly one persisted ordinal".
      AC: inserting the first litter into a freshly migrated database yields
      `litter_code = 'BIZ'`; `litters.seq` is the ONLY persisted ordinal (no
      second counter column, no base-26 intermediate stored anywhere) and
      `encodeLitterCode(seq) = litter_code` holds for every row; 1000
      consecutive inserts are pairwise distinct, all match `^[A-Z]{3,5}$`, and
      `ORDER BY seq` equals `ORDER BY length(litter_code), litter_code
      COLLATE "C"`; the AZZ→BAA and ZZZ→AAAA boundaries encode with no length
      bug.
