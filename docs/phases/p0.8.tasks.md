### P0.8 Visual cage management — P0-c (MVP v0.3)

- [ ] Visual cage-management view (location/room layout of cage grid); cages
      render their slots (R1); mouse chips render within their slot when
      slot_id is set, else at cage level.
      AC: every non-deleted cage renders under its location with its
      non-deleted slots; mouse chips reflect current mouse.cage_id and, when
      set, mouse.slot_id.
- [ ] transfers table — MUTABLE (`deleted_at`): mouse_id FK mice,
      from_cage_id, to_cage_id, status TEXT default 'pending'
      (pending|committed|cancelled), idempotency_key UUID UNIQUE,
      initiated_by/at, resolved_by/at, mouse_move_id FK (set on commit). NO
      status column is added to the `mice` version rows beyond transit_status —
      schema-unchanged.
      AC: duplicate idempotency_key insert rejected; `mice` schema
      byte-identical to P0-a; transfers rows soft-delete via deleted_at.
- [ ] Pending-transfer transitions (service): INITIATE = INSERT
      transfer(pending) + audit(action='transfer_initiate') — NO mouse_move,
      NO cage_id change (mouse.cage_id stays = origin until confirmed).
      COMMIT (one tx) = validate from_cage_id = mouse.cage_id; INSERT
      mouse_move; UPDATE mouse.cage_id=to; UPDATE transfer SET committed,
      mouse_move_id, resolved_* WHERE id=$ AND status='pending'; INSERT
      audit(action='transfer_commit'). CANCEL = UPDATE transfer SET cancelled,
      resolved_* WHERE id=$ AND status='pending' + audit; no mouse_move,
      cage_id untouched.
      AC: commit produces exactly the P0-a move writes (mouse_move + cage_id +
      audit) plus the resolved transfer row, atomically; commit/cancel replay
      against a non-pending transfer is a no-op; stale pending (mouse moved
      since initiate) fails validation and writes nothing (plan Open
      Question 17).
- [ ] Pending-transfer visualization (from `transfers WHERE status='pending' AND
      deleted_at IS NULL`): ORIGIN cage shows solid mouse chip (via
      mouse.cage_id) + "transfer tag" (from_cage_id=:cage); DESTINATION cage
      shows dimmed/ghost chip (to_cage_id=:cage).
      AC: while pending, the mouse renders solid at origin with tag and dimmed
      at destination; after commit or cancel both markers clear.
- [ ] Drag-and-drop move (reuses the P0-a MOVE transaction + idempotency_key);
      a drop can fire the instantaneous move OR open a pending transfer —
      recommendation: simple drop = instantaneous, explicit "start transfer" =
      pending (plan Open Question 16).
      AC: a drop produces exactly the same DB writes as the P0-a move flow
      (cage_id update + mouse_move + audit rows); double-drop guarded by
      idempotency_key.
