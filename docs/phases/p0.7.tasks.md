**PATTERN (third occurrence, 2026-09-22): this task family keeps shipping ACs
that cannot be met or cannot fail — (1) step 9's "grep `renderedId` returns 0"
was vacuously true after the step-5 rename; (2) deleting `MouseCell.mouseLabel`
had no task at all; (3) step 8's `< 300 lines` was left unmet at close and
deferred in a STATUS clause instead of a task (now 8b), and 9b's "edit `sex`
via inline edit" named a UI control that does not exist (now a store-level
probe, see 9b). The common cause is an AC naming a symbol/control/number that
was never checked against the code at the moment of writing.
FOURTH OCCURRENCE — A NEW VARIANT (2026-09-22): (4) step 8's "every mouse
created via `addMouse` has exactly one 'toe' punch" asserted BEHAVIOUR THAT WAS
NEVER IMPLEMENTED AT ALL — the first of this family where the AC described a
feature that does not exist rather than mis-naming one that does (now 8c). It
survived several reviews because step 5's AC makes a toe-only mouse render
identically to a zero-punch mouse, so the label projection masks the defect BY
CONSTRUCTION; only direct `punches` inspection could ever catch it. Lesson on
top of the one above: when a criterion is INVISIBLE in the rendered output,
its AC must inspect the field, never the render.
SAME SHAPE, file-name variant (2026-09-22, found at 9b's close): 9b's body
listed `MouseCaseDrawer.client.tsx` and `TasksView.client.tsx` as migration
sites. NEITHER holds a `MouseCell` — both render PERSISTED SNAPSHOT strings
(`target.label`, `task.subjectLabel`), so there was nothing to migrate and the
developer correctly left them alone. File names written into a task without
being opened, exactly like symbols written into an AC without being grepped.
FIFTH OCCURRENCE — BARE-IDENTIFIER GREP VARIANT (2026-09-22, found at 9d's
close): (5) 9d's AC said "grep `mouseLabel` under `packages/types/src` returns
0". It returns **2**, and BOTH hits are legitimate — `grid.ts:27` was PROSE about
the field 9b deleted (since repaired, `afa8c43`), and the other names the
surviving `lib/mouseLabel.ts` MODULE, which 9b's own AC required keep existing.
The INTENT was met in full; the AC was UNMEETABLE AS WRITTEN. What makes this
instance the instructive one: 9b's AC already carried the warning, verbatim, in
this same file — "(Do NOT assert 'grep `mouseLabel` returns 0' — `ParentCell.mouseLabel`
and the `@/lib/mouseLabel` module legitimately survive.)" — and the very next task
made the exact mistake the warning names. A warning one task above is not a
guard. Variant: an AC grepping a BARE IDENTIFIER that legitimately appears in
prose and in a MODULE NAME. Remedy: grep a DECLARATION, not a word — 9d's AC is
RESTATED (on 9d, archived) as "no `mouseLabel:` key declaration".
SIXTH OCCURRENCE — A NEW SUB-SHAPE (2026-09-22, found when step 6's developer
flagged it): (6) **an AC that silently MANDATES A SCHEMA CHANGE because the state
shape it operates on has no room for what it demands.** Step 6's AC (written
2026-09-16) said `removePunch` "shrinks that mouse's ACTIVE punches by 1 **while
the row survives with deletedAt set**". `removePunch` is a pure function whose
entire output is `ColonyGrid`, so there is NOWHERE for the row to survive EXCEPT
`MouseCell.punches` — the AC therefore forced `MouseCell.punches` to carry
tombstones, against plan §4 ("active rows only"), against `0026_punches.sql`'s
`WHERE deleted_at IS NULL` partial index, against `grid.ts`'s "no `deleted_at`
reaches the client" header, and against `rules/core.md`'s "mask at read". The
developer had no other reading available and FLAGGED it rather than hiding it —
correct on both counts. Resolved by the owner as option B (step 6a).
DISCRIMINATING TEST APPLIED: was the sentence false the day it was written? YES
— plan §4 already said active-only on 2026-09-16. So this is PATTERN, not DRIFT.
THE CROSS-CHECK THAT WOULD HAVE CAUGHT IT: before writing an AC that constrains a
field, grep the PLAN for that field's OWN DEFINITION ("active rows only") and
check the AC does not contradict it. Lesson on top of the five above: it is not
enough for an AC to name symbols that exist — it must also fit in the state shape
those symbols live in, or it quietly redesigns that shape.
SEVENTH OCCURRENCE — SUB-SHAPE: **an AC that greps a PHRASE which a LATER TASK
MADE TRUE AGAIN** (2026-09-22, found at task 11's close). (7) Task 11's AC (5)
said "grep `the sex editor below|drawer itself writes a patch` returns 0",
requiring two stale comment phrases be reworded in 11's own diff. One phrase
(`MouseDetail.client.tsx:69`, "the sex editor below never fires for a mouse it
can't find") was genuinely FALSE and was rewritten (`5f4586d`) — there is a sex
editor again and Save DOES fire on the not-found path, returning `{ok:false}`.
The other (`:24`, "the drawer itself writes a patch via the store") was false
when 11 landed and **became TRUE again when task 13 shipped the drawer that
writes exactly that patch** — so the grep could only be satisfied by DELETING A
TRUE COMMENT. DISCRIMINATING TEST APPLIED (as the SIXTH did): was the sentence
false the day it was written? **YES — the FORM was.** A phrase grep cannot
distinguish "the comment was removed" from "the comment became true again", so
it was never the right instrument; this is the same class as the FIFTH
(bare-identifier grep), one level up — there the identifier was legitimate, here
the CLAIM is. So PATTERN, not DRIFT. REMEDY, and 11's AC (5) is RESTATED to it:
**assert the PROPERTY ("no comment in this file makes a false claim"), never the
ABSENCE OF A STRING.** Lesson on top of the six above: an AC that greps text a
sibling task may legitimately re-introduce has a lifetime shorter than the task
family it lives in. The trigger that exposed it was an L4 SEQUENCING SLIP — task
13 shipped while its blocker 11 was still `[~]` (recorded on both tasks, remedied
by 11's close) — but the slip is the exposure, not the cause: the AC was already
the wrong instrument.
DRIFT is a DIFFERENT CLASS, ruled here so it is not re-argued as ANOTHER
numbered occurrence (2026-09-22; written when the sixth had not yet been found —
it is not the sixth, the schema-mandate above is): the three stale references `afa8c43` fixed — the `plan §7`
citation, `grid.ts` prose pointing at a retired function, and the five/six
tolerated-forms count — were all TRUE WHEN WRITTEN and went stale when their
referent was retired. The PATTERN above is WRONG-AT-WRITING; this is
CORRECT-THEN-STALE. Discriminating test: was the sentence false the day it was
written? Yes → PATTERN. No → DRIFT. Different cause, but ONE shared remedy: grep
the referent when you write it AND again when you retire it. 9c's body already
names this class ("a header describing a function that is gone is the same drift
class this task closes").**
