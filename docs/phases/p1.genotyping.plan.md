- **Per-gene 2-allele genotype model (POLICY + design, user 2026-09-15; architect
  designed).** Mice are diploid → store each mouse-gene as TWO alleles (one per
  homologous chromosome), NOT a single `f/+` text token. RE-NORMALIZES the
  current schema where `genes.code` bakes zygosity into the whole marker.
  - **Schema**: `genes.code` → BARE gene (`Nf1`, `PlpCre`, `Ai14`); add
    `genes.kind` (`'locus'` | `'transgene'`, DISPLAY-only). `mice_genes` gains
    **`allele_maternal`, `allele_paternal`** (0015 convention: nullable →
    backfill → later NOT NULL DEFAULT `'?'`).
    RENAMED 2026-09-17 from `allele_a`/`allele_b`: the pair is ORDERED and the
    order MEANS parent of origin (below), so `a`/`b` names a column that now
    carries a fact — and a generic name is exactly how someone fills it
    backwards (CLAUDE.md §10 forbids generic names).
    Keep `order_index` + its partial-UNIQUE + soft-delete.
    Allele type = TEXT (NOT enum/lookup yet — P1 genotyping's `(-)`/`?`/`dnw`
    vocab is still moving; lookup table is the P1 upgrade point).
  - **Allele vocab**: `+` = normal/WT, `f` = floxed (engineered), `-` =
    null/KO, plus `G` etc. Whole-genotype unknown STILL = 0 `mice_genes` rows → `'?'`.
  - **~~Canonical order~~ — DELETED 2026-09-17 (user). THE PAIR IS ORDERED:
    first = MATERNAL, second = PATERNAL.** `f/+` (maternal floxed) and `+/f`
    (paternal floxed) are DIFFERENT mice, not two spellings of one. The old rule
    ranked `f < + < - < G < … < ?` and stored the lower rank first, which would
    silently REWRITE `+/f` as `f/+` — destroying parent of origin with no way to
    recover it. It is gone; nothing sorts the stored pair. (`f/f` and `+/+` are
    unaffected — only heterozygotes carry the distinction.)
  - **Colour resolves from a SORTED COPY, never from the stored pair.** The rank
    existed for one reason: the composed genotype string is the GENO **colour
    key**, so two spellings of one mouse would split into two colours. Keep that
    property without touching storage — sort a throwaway copy at colour-lookup
    time only. Storage keeps parent of origin; `f/+` and `+/f` still resolve to
    the SAME colour, which is right because the functional genotype is the same.
    The 7 seed GENO keys still reproduce.
  - **Unknown parent of origin — POLICY (user, 2026-09-17): staff or the
    professor fills it in MANUALLY.** The system never guesses it and never
    infers it from the line. Imported, outside-origin and unknown-parent mice
    have no data to derive it from. UI consequence: for a mouse with unknown
    parents the picker must NOT pre-fill an order — start both alleles at `'?'`
    and make the human choose, so a guess is never recorded as a fact.
  - **Transgene**: `PlpCre`/`ccEGFP` are hemizygous transgenes — store uniformly
    as 2 alleles (`(Tg,0)` present → renders bare `code`; `(Tg,Tg)` → `code(hmo)`),
    DISPLAY branches on `genes.kind`. (OQ — professor.)
  - **DTO**: `GeneCall {code, alleleMaternal, allelePaternal, display}` (was
    `{code, allele}`; the a/b naming is retired with the columns);
    `MouseCell.genotype` flat string + `genotypeColor` UNCHANGED — composed at
    READ from the structured alleles (join per-gene `display` by `order_index`
    with `;`), so the GENO colour key still matches.
  - **Item 4 picker**: gene → zygosity quick-pick. The list is now ORDERED —
    `f/+` and `+/f` are SEPARATE choices (maternal first), so a heterozygote
    offers both directions. (`+/+`,`f/+`,`+/f`,`f/f`,`+/-`,`-/+`,`?/?`;
    transgene = present/`hmo` toggle) → pure fn expands to
    `(alleleMaternal, allelePaternal)`;
    `'?'` + free-text input kept as escape hatch. Mock-era client-composes the
    flat string into `addMouse({genotype})`; server-era POSTs structured `genes[]`.
