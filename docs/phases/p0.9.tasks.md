### P0.9 Task model v2 — cases + child tasks (DECIDED 2026-09-13, REFINED 2026-09-13 — plan §4 Task model v2)

Lifecycle todo → doing → done → verified, cancelled = side-exit.
REFINED 2026-09-13 (user): the earlier `task_events` table is RENAMED to child
**`tasks`** — IMMUTABLE, append-only STATUS RECORDS under a case (each row =
the status the case moved to + case_id + actor + note + created_at; status is
assigned at creation and NEVER changes — redundant with the case's status by
design, a useful audit trail). `cases` = stable work-item identity + MUTABLE
`current_status` rollup (advance = INSERT one child task + UPDATE the rollup,
ONE service tx). Creating work = a case + its FIRST `todo` task; SOP
generators do the same; a batch over N mice = N separate cases (one per
mouse), each with its own first task.
